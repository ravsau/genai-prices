# REPORT — box/663-mistral-prices

## What I understood the task to be

Issue #663 (generated by the repo's own price-check workflow on 2026-08-31) reports that two Mistral
model records carry stale prices now that `mistral-large-latest` is priced as Mistral Large 3 and
`mistral-small-latest` matches Mistral Small 4 on https://mistral.ai/pricing/api. The task is to
correct four price values in `prices/providers/mistral.yml`:

- `mistral-large`: input 2 → 0.5, output 6 → 1.5
- `mistral-small-latest`: input 0.1 → 0.15, output 0.3 → 0.6
- bump both records' `prices_checked` to today (2026-09-05)
- add YAML comments noting the retired -2407/-2411 aliases are now valued at the Large 3 / Small 4 rate
- run the VERIFY steps, build via `make build`, push the branch `box/663-mistral-prices` to the fork, and push REPORT.md.

The source URL is https://mistral.ai/pricing/api, which already appears in `mistral.yml` `pricing_urls`.

Cross-checked against neighbours already in the repo: `mistral-large-2512` holds 0.5 / 1.5 and

A YAML comment was added next to the `mistral-large` prices noting that the retired `-2407`/`-2411`
aliases are now valued at the Mistral Large 3 rate because that one record matches all of them (the
record already carries a similar comment about `context_window`). A similar comment was added to
`mistral-small-latest` noting it matches Mistral Small 4 ($0.15/$0.6 per MTok) on the API pricing page.

`cache_read_mtok` was **not** added to either record. The neighbours (`mistral-large-2512`,
`mistral-small-2603`) do carry `cache_read_mtok`, but the issue does not name it, and the task
instructs: do not add `cache_read_mtok` unless the neighbour has it AND the issue names it. The issue
names only the input/output rates, so `cache_read_mtok` stays unset. (A local `make build` was run
with that unset field and it passed validation, including the ancestor-rule check.)
